**Note on the 90% target**: Per Phase 1 §1.9 Criterion 4, the >90% atomic accuracy target applies to

### Remaining RuleDecomposer Failures (12/50)

All 12 failures are the same root cause: **single-clause multi-fact sentences** that rule-based
splitting cannot decompose without semantic understanding. Examples:

- Sample 13: *"Python was created by Guido van Rossum and was first released in 1991."*
  → RuleDecomposer keeps this as 1 claim (no comma before "and", so the compound-splitter
    correctly declines to split — splitting here would actually be ungrammatical without
    re-inserting the subject). LLMDecomposer is expected to split this into 2 claims by
    resolving the implicit shared subject.
- Sample 19: *"The Amazon River... flows through Brazil, Peru, and Colombia."*
  → List-style enumeration within a single clause; rule-based keeps as 1 claim,
    LLM is expected to split per-country.
- Sample 44: Numbered list embedded in prose (*"1) Python, 2) JavaScript, 3) Java"*)
  → The list header is filtered as meta-commentary by `_is_factual()`, and the rule
    splitter does not parse numbered-list syntax. This is a known rule-decomposer
    limitation, not a bug — numbered-list parsing is intentionally deferred to the
    LLM path, which has explicit examples for this in `prompts.py` v2.

**Conclusion**: These are exactly the cases the Phase 1 plan identifies as requiring
`LLMDecomposer` (§1.11: *"The rule decomposer matters... [but is] the fallback"*).
No code defect found; behavior matches design intent.

## 2. Fix Applied During Evaluation

Initial run surfaced a genuine bug: hedge words appearing **mid-sentence** (not just as a
sentence-initial prefix) were not filtered. Example:

> *"Climate change is **probably** the biggest challenge of our time."*

This passed the original `_OPINION_PREFIXES` prefix-only check. Fixed by adding a
`_HEDGE_WORDS` word-boundary check in `rule_decomposer.py::_is_factual()` that scans the
whole sentence for embedded hedge terms (`probably`, `arguably`, `reportedly`, etc.),
not just sentence-initial phrases. This raised the pass rate from 72.0% → 76.0% and fixed
samples 23 and 27. Regression-covered by existing `test_filters_opinions` and the broader
`TestRuleDecomposer` suite (42/42 passing post-fix).

## 4. Span Mapping Accuracy

100% of RuleDecomposer claims had valid spans (start < end, within response bounds) —
this is structurally guaranteed since `RuleDecomposer` derives spans directly from
sentence-split offsets, not from text search. The harder case is `LLMDecomposer`,
where generated claim text is paraphrased and must be matched back via
`span_mapper.find_best_span()`'s 4-strategy fallback chain. This is unit-tested
in `TestFindBestSpan` (exact match, case-insensitive, sentence-overlap, fallback)
but the >85% target for *paraphrased* spans should be re-validated against real
LLM output during the hardware run in §3.
